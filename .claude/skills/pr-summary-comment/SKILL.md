# PR summary comment

Write the comment in **English**, even if the user writes in another language.
If a Vietnamese (or other) version was already posted, edit that comment in place
with `update_issue_comment` instead of adding a second one.

## Gather facts first
- `git log --oneline main..HEAD` and `git diff --stat main..HEAD` for scope.
- `pull_request_read` (get) for `mergeable_state`, labels, head SHA.
- Only report tests that were actually run. If the repo has no automated tests, say so.
- Say plainly what was NOT covered and why (e.g. real device, real API).

## Structure (use these headings, in this order)
1. `## Pre-squash-merge summary` — one line of scope: commits, files, lines, base SHA, conflicts or not.
2. `### Changes` — table `| # | Problem | Fix | File |`. Include regressions found and fixed during testing as their own row.
3. `### Test results` — table `| Area | Scope | Result |`, with a final "Not covered" row.
4. `### Notes, not caused by this PR` — table `| Item | Description | Severity |`. Omit the section if empty.
5. `### Squash merge suggestions` — proposed title (ends with `(#<PR number>)`), what to keep in the squash body, what to drop (e.g. fixes for bugs introduced only on the branch), and any post-deploy step.

## Posting
- New comment: `add_issue_comment` (a PR number is an issue number). Edit: `update_issue_comment`.
- The comment MUST end with exactly this footer:

```

---
_Generated by [Claude Code](https://claude.ai/code)_
```

- Do not merge as part of this skill. Only comment.
- Report the comment URL back to the user in one or two lines.
